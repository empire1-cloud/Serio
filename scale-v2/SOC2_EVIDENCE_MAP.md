# SOC 2 Evidence Map — FABLE-5 / Economic Truth

This file connects Empire-1's existing SOC 2 readiness work to the live Economic Truth control plane. It is an evidence map, not a certification claim. A SOC 2 Type II report must be issued by an independent CPA firm after evaluating control design and operating effectiveness over the audit period.

## System of record

FABLE-5 is the authorization and evidence gate. SLA113 is the Economic Truth lifecycle/receipt authority boundary. Archisynapse and connected payment rails provide execution/ledger evidence. Lyrica/VICS can contribute provenance evidence. The Receipt Graph binds these facts into a verifiable history.

The governing rule is: a policy document is not evidence that a control operated. A control event must produce or reference a receipt.

## Receipt proof contract

For a newly created receipt, the authoritative digest is generated by FABLE-5, not accepted from the caller. The caller/provider digest is retained separately as `source_digest`.

A proof bundle contains:

- canonical receipt envelope
- `receipt_hash`
- `previous_hash` and `chain_sequence`
- detached Ed25519 signature
- signing key ID
- public-key fingerprint
- public key

`GET /api/receipts/:id/verify` recomputes and verifies the proof and chain neighbors. `GET /api/receipts/verify-chain` verifies the tenant chain. `scripts/verify-receipt-proof.js` verifies an exported proof outside the running service.

Any change to a signed field, chain link, or signature causes verification to fail.

## What this closes

This closes the technical statement: **"Can you prove the receipt is tamper-evident?"**

The proof is cryptographic and independently verifiable with the pinned public key/fingerprint.

## What this does not close

This does not by itself produce a SOC 2 Type II attestation. The remaining compliance program includes the existing Empire/Claude SOC 2 readiness materials: scope, policies, control ownership, vendor review, evidence sampling, operating-period collection, remediation, management representations, and the independent audit.

It also does not make the database physically immutable. Tamper-evident means unauthorized modification becomes detectable. Stronger historical non-repudiation can be added by periodically publishing signed Receipt Graph checkpoints to an independent external anchor.

## Production requirements

Before describing production receipts as cryptographically tamper-evident:

1. Generate an Ed25519 signing key outside the repository.
2. Store the private key in the production secret manager/KMS boundary; never commit it.
3. Set `RECEIPT_SIGNING_PRIVATE_KEY_B64` and a versioned `RECEIPT_SIGNING_KEY_ID`.
4. Publish/pin the corresponding public-key fingerprint for enterprise verifiers.
5. Run the full tenant Receipt Graph verification and retain the result as evidence.
6. Exercise key rotation (`RECEIPT_KEY_ROTATION.md`) and recovery as controlled, receipted operational procedures.
7. Record backup/restore and tenant-isolation tests as evidence records, not screenshots alone.
